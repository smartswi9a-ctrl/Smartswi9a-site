# Traduction du site — état et décisions

Document de suivi de l'internationalisation (FR / AR / EN) de Smartswika.
Dernière mise à jour : 2026-11-17.

---

## 1. Architecture actuelle

Deux systèmes de traduction coexistent. C'est volontaire, mais c'est une
source de bugs : **une clé ajoutée dans un système est invisible dans l'autre.**

| Contexte | Mécanisme | Fichier |
|---|---|---|
| Site client (accueil, boutique, produit, panier, blog, villes) | `data-key` + `applyTranslations()` | `translations.js` |
| Dashboard vendeur | `tr()` + `data-i18n` (système legacy) | `js/translations-vendor.js` |
| Pages autonomes (404, reset, vendeur, CGU) | `initLangToggle()` | `js/lang-toggle.js` |

### Attributs reconnus par `applyTranslations()`

- `data-key` → `textContent` (ou `innerHTML` si la clé finit par `Html`)
- `data-aria-key` → attribut `aria-label`
- `data-placeholder-key` → attribut `placeholder` *(ajouté en PR #82)*
- `data-title-key` sur `<html>` → `<title>` de la page *(utilisé par `lang-toggle.js`)*

### Clés

**À date : 738 clés × 3 langues, 0 manquante.**

Toute clé ajoutée doit être ajoutée **dans les 3 blocs** (`fr`, `ar`, `en`) de
`translations.js`. Les trois blocs sont dans ce fichier, dans cet ordre.

## 3. Décision : les CGU restent en français

### Le constat

728 textes juridiques répartis sur 4 documents :

| Page | Textes |
|---|---|
| `cgu-acheteur.html` | 159 |
| `cgu-vendeur.html` | 247 |
| `contrat-vendeur.html` | 210 |
| `politique-confidentialite.html` | 112 |

### La décision

**Ne pas traduire automatiquement.** Une traduction machine non relue d'un
contrat crée un risque réel : si la version arabe et la version française
divergent, même légèrement, l'éditeur s'expose en cas de litige.

### Ce qui a été fait à la place

1. **Sélecteur de langue ajouté** sur les 4 pages — la navigation reste
   cohérente dans tout le site.
2. **Bandeau d'avertissement** affiché **uniquement en AR et EN** :
   > ⚠️ **Version de référence** — Seule la version française de ce document
   > fait foi. La traduction intégrale est en cours de validation juridique.

   Visible via `#legalLangNotice` (masqué en FR par `js/lang-toggle.js`).
3. **Titre de l'onglet traduit** (`data-title-key` sur `<html>`).

### Ce qu'il reste à faire pour publier les CGU en AR/EN

1. Lancer `node scripts/apply-legal-i18n.cjs` — pose les `data-key` et extrait
   les textes FR dans `docs/i18n-legal-fr.json`.
2. Faire traduire ces textes par un **juriste arabophone** (et anglophone).
3. Injecter les traductions dans les blocs `ar` et `en` de `translations.js`.
4. Retirer le bandeau `#legalLangNotice` des 4 pages.

**Ne pas sauter l'étape 2.** Un contrat se relit avant publication.

## 5. Pièges connus

1. **Ne jamais utiliser `Set-Content -Encoding UTF8`** sur `admin.js` ou les
   fichiers contenant des accents/emojis → double encodage (`Ã©` au lieu de `é`).
   Utiliser `[System.IO.File]::WriteAllText($path, $text, (New-Object System.Text.UTF8Encoding($false)))`.

2. **Pas d'apostrophe non échappée** dans `functions/index.js` : le test
   `livo-webhook-sim` casse.

3. **Toute nouvelle clé = 3 langues.** Vérifier la parité après chaque ajout :
   ```powershell
   node -e "const fs=require('fs'),vm=require('vm');const sb={window:{}};vm.createContext(sb);vm.runInContext(fs.readFileSync('translations.js','utf8'),sb);const T=sb.window.translations;const all=new Set();Object.keys(T).forEach(l=>Object.keys(T[l]).forEach(k=>all.add(k)));['fr','ar','en'].forEach(l=>console.log(l,Object.keys(T[l]).length,[...all].filter(k=>T[l][k]===undefined).length+' manquante'))"
   ```

4. **Un libellé généré en JS ne passe pas par `data-key`.** Il faut soit le
   passer par `t()`, soit exposer `window.__onLangChange` pour re-rendre.
